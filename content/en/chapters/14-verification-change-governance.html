Control-System Verification, Change Management, and Governance

Learning objectives

Distinguish verification (“was the system implemented as specified?”) from validation (“is it fit for its intended process decision?”). Build evidence for monitoring and control changes across requirements, data, model, software, equipment interface, human response, and rollback. Govern a system throughout its lifecycle rather than treating successful installation as release evidence.

A fab control system includes more than an algorithm: sensors and calibration, data mapping, context, recipe identity, feature code, thresholds, model version, alarm presentation, controller interface, permissions, procedures, and records. Assign an owner and controlled revision to each critical element. A version label on the model is not sufficient if the feature extraction or upstream source changed independently.

Evidence layers and controlled change

Start from a decision requirement: what condition is detected, for which product/tool/recipe population, with what latency, and what human or automatic action follows? Translate it into testable requirements for data completeness, timestamp association, units, valid operating modes, missingness, false alarms, detection behavior, constraints, access, and auditability. Verification checks the implementation against those requirements. Validation examines whether the requirements and resulting behavior answer the actual engineering need. Both need representative data and explicit assumptions.

A proportionate evidence stack includes: static/configuration checks; unit tests of transformations and calculations; replay against versioned synthetic or approved historical records; boundary and fault-injection cases; integration checks for event lineage and permissions; human-factors review of alarms and procedures; shadow operation; and staged authorized deployment. For a fitted model, inspect residuals and operating-range coverage; a high R² alone does not validate it. Include sensor failure, missing/out-of-order data, recipe transition, maintenance reset, saturation, and recovery scenarios. Record expected outcomes before executing the tests.

Change control should identify request and rationale, affected components and populations, risk assessment, independent reviewers, approval authority, test evidence, release identifier, effective time, rollback path, and post-change monitoring window. A feature update can change an alarm even when the model weights are unchanged. A sensor replacement, baseline refresh, recipe revision, or threshold edit is also a controlled change when it can alter a decision. Emergency changes need a defined retrospective review, not an undocumented bypass.

Separate development, approval, and production privileges where feasible. Log who changed a model or setpoint, what changed, why, when it became active, and what process outcomes followed. Preserve an immutable prior configuration and the ability to return to it. Define rollback triggers and the safe state for partial deployment. A rollback restores software configuration; it does not reverse wafers already processed, so material containment and lot traceability remain separate duties.

Monitor after release for input drift, missingness, alarm burden, intervention outcomes, controller movement, and subgroup performance across tools/products. Reverification and revalidation are warranted after material changes in sensors, recipe, measurement, code, operating mode, or target population. Governance must specify who can suspend the function, who dispositions affected material, and how lessons update requirements without silently changing the historical evidence.

Worked example: a new endpoint feature

A team proposes adding a trace-derived endpoint slope to a chamber FDC model. Before release, define units (for example, sensor units/s), trace window boundaries, signal calibration, recipe phases, minimum sample count, missing-data behavior, threshold version, and intended response. Verification replays a pinned dataset and synthetic edge cases with expected feature values; it tests flat traces, a known linear ramp, missing samples, duplicate timestamps, and a phase boundary. The ramp case uses x(t)=3+2t sensor units over seconds, so the expected slope is 2 sensor units/s under ordinary least-squares on exact equally spaced samples.

Validation then asks whether the feature adds useful discrimination on a held-out, representative population without unacceptable false alarms or subgroup failure. A replay is not evidence of causal diagnosis or silicon benefit. Run in shadow mode, compare alerts with independently reviewed outcomes, and authorize a limited staged release only through the site’s approval process. If event lineage breaks or data coverage falls below the declared minimum, the model should abstain or enter its documented fallback, not emit a confident normal result.

Governance boundaries

Testing cannot prove safety for every unobserved state. Historical data may underrepresent rare faults or changed populations. A process-control model, security change process, alarm standard, and safety lifecycle have different scopes; meeting one does not establish compliance with another. Adapt governance to the fab’s hazard, quality, regulatory, cybersecurity, and equipment requirements. This chapter is an educational framework, not certification, legal advice, or a substitute for controlled site procedures.

Review questions

  1. Give one example each of verification and validation for the endpoint feature.
  2. Why is a high R² insufficient release evidence?
  3. Which changes require control even if model weights are unchanged?
  4. What is the difference between software rollback and material containment?
  5. Define a measurable condition under which the system should abstain.
